🧠 What Is SOC Alert Triage?

Alert triage is the process of reviewing security alerts and determining which ones require further investigation.

A SOC can receive hundreds or thousands of alerts.

Not every alert represents a real security incident.

For example:

1000 alerts
     ↓
Detection Rules
     ↓
Security Alerts
     ↓
SOC Analyst
     ↓
Investigate
     ↓
True Positive / False Positive

The analyst's job is to separate meaningful security incidents from legitimate activity and unnecessary alerts.

This helps security teams focus their time on events that actually require attention.

🔎 Understanding True Positive vs False Positive

Two important terms used during this exercise were:

True Positive

A detection correctly identifies suspicious or malicious activity.

Example:

Suspicious phishing email
        ↓
Investigation confirms malicious intent
        ↓
TRUE POSITIVE
False Positive

A detection triggers, but investigation shows that the activity is legitimate.

Example:

Security rule detects unusual process
        ↓
Investigation shows legitimate administrator activity
        ↓
FALSE POSITIVE

This distinction is extremely important in SOC operations.

Too many false positives can create alert fatigue, where analysts spend too much time investigating harmless events.

4. Analyzing the Phishing Indicators

Several characteristics in this email deserve attention.

🚩 Unexpected inheritance claim

An unexpected inheritance message is a common social-engineering technique.

🚩 Request for banking information

The email attempts to obtain sensitive financial information.

🚩 External sender

The sender is outside the organization.

🚩 Unusual subject

The subject attempts to attract the recipient's attention using an unrealistic inheritance story.

These indicators should cause a SOC analyst to investigate further.

A useful phishing investigation mindset is:

Who sent the email?
        ↓
Who received it?
        ↓
What is the subject?
        ↓
What does the message request?
        ↓
Are there links or attachments?
        ↓
Is the sender/domain trustworthy?
        ↓
Does other evidence support the alert?
        ↓
TP or FP?

7. Documenting the Investigation

The incident report provides a section for the analyst to explain the classification.

A good SOC investigation note should answer:

When did the activity occur?
Which entities were involved?
What evidence was observed?
Why was the alert classified as TP or FP?
What additional investigation was performed?

For example:

Time of Activity:
09/07/2026 08:29:02.720

Related Entities:
eileen@trendymillinercy.com
support@tryhatme.com

The most important part is the closure rationale.

A weak rationale would be:

"This is a false positive."

A stronger rationale explains why:

"The alert was reviewed against the available email evidence. The sender, message content, and requested information were analyzed to determine whether the activity represented legitimate communication or phishing behavior."

The goal is to make the investigation understandable to another analyst who reads the case later.

11. Why Parent-Child Process Relationships Matter

A parent-child process relationship describes which process started another process.

For example:

powershell.exe
      |
      +---- net.exe
      |
      +---- whoami.exe

This is useful for security monitoring because attackers frequently use legitimate operating-system tools after gaining access to a system.

Commands such as:

whoami
net

can be used for system and account discovery.

However, seeing these commands does not automatically prove malicious activity.

A SOC analyst should investigate:

Which user launched PowerShell?
What was the PowerShell command?
Was the activity expected?
What happened before the process was created?
What happened afterward?
Was the host already associated with another alert?
Are there authentication or network events supporting the activity?

This is an excellent example of why context and correlation are important.

🧠 What I Learned
Alert names are not enough

An alert titled:

Suspicious email from external domain

does not automatically mean the email is malicious.

The analyst needs to inspect the underlying evidence.

Severity does not tell the whole story

The alerts in this scenario were shown as Low severity, but that does not mean they should automatically be ignored.

Severity is one input into triage; context and evidence matter as well.

Process relationships provide valuable context

Instead of looking only at:

net.exe

we can investigate:

powershell.exe
       ↓
net.exe

The relationship can reveal more about how an action occurred.

Documentation is part of security operations

Investigation isn't finished when the analyst understands the alert.

The reasoning also needs to be documented so another analyst can understand the decision.

📌 Key Takeaways

The biggest lesson from this exercise was understanding the SOC investigation mindset:

Don't just ask:
"What alert fired?"

Ask:
"Why did it fire?"
        ↓
"What evidence supports it?"
        ↓
"Is the behavior expected?"
        ↓
"What else should I correlate?"
        ↓
"What action should be taken?"

This is the difference between simply viewing alerts and actually performing security analysis.
